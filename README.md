# Ништяк — повтори мой эксперимент

Сервис готовит переносимый пакет небольшого Python-проекта: исходники, README с запуском, зависимости, отчёт и, когда подбор успешен, точные версии с хешами. Загруженные скрипты на сервере не выполняются.

## Как пользоваться

1. Соберите исходники и пример данных в один ZIP до 10 МиБ и загрузите его. Сохраняйте относительные пути файлов.
2. Сервис статически разбирает импорты и локальные модули, метаданные, возможный запуск и пути к данным.
3. Поставщики импортов проверяются по сведениям автора, опубликованным метаданным и структуре wheel. Совпадение имени импорта с названием пакета само по себе остаётся гипотезой. Затем `uv` подбирает совместимые версии прямых и транзитивных зависимостей.
4. Если остались пробелы, DeepSeek делает до двух общих проходов по проекту. Предложенные пакеты проходят ту же проверку опубликованных метаданных и каталога wheel через HTTP Range, без установки и полной загрузки архива; версии выбирает `uv`. Частичное чтение не подтверждает хеш всего wheel или работоспособность кода. Если сведения недоступны, соответствие остаётся неподтверждённым.
5. Всё нерешённое собирается в одну форму. Поля необязательны: можно добавить пояснение своими словами или продолжить с неизвестными сведениями. Ответы сохраняются одной отправкой.
6. После ответа выполняется один финальный проход DeepSeek и повторная проверка среды. Нового автоматического опроса нет: сервис собирает ZIP либо объяснимый черновик. Небезопасные файлы остаются блокирующим условием.
7. Посмотрите русский README и целевую среду, скачайте пакет и повторите установку и запуск в новом виртуальном окружении. В списке архива можно открыть любой файл: Markdown отображается как документ, код — с подсветкой, номерами строк и копированием. Результат ручной проверки можно записать на странице архива.

Недостающие данные и локальные модули можно добавить, заменив ZIP в том же проекте. Совместимые сведения автора сохраняются; устаревшая проверка прошлого архива помечается отдельно. Секрет или повреждённый исходник блокирует сборку до исправления файла и не маскируется под доступный черновик.

Python и ОС выбираются вместе в одном блоке целевой среды. После применения сервис повторяет статический анализ и автоматически подбирает зависимости; совместимые сведения автора и исключения файлов сохраняются. Найденная команда запуска доступна сразу, ручные изменения запуска и зависимостей — в экспертных настройках. Данные для README заполняются по анализу, дополнения автора необязательны. Отсутствующие данные и лицензия остаются предупреждениями; сервис их не выдумывает. Сетевая ошибка или неподдерживаемый формат дают объяснимый черновик.

В корне ZIP создаются `requirements.txt`, `pyproject.toml` и `environment.yml`. После успешного подбора добавляется `requirements.lock.txt` с точными версиями и хешами; для поддерживаемого Linux-профиля — Dockerfile. `pyproject.toml` описывает зависимости, а `environment.yml` позволяет подготовить отдельную Conda-среду с установкой того же pip-lock. Это новый профиль среды, а не восстановленные метаданные автора или полный Conda-lock. В черновике README объясняет, что осталось неопределённым; команды установки выдаются для проверенного lock.

README описывает файлы итогового ZIP и альтернативные способы подготовки среды. Исходные конфигурации автора сохраняются в `project/`: создание его Conda-среды, установка локального пакета и сборка авторского Dockerfile требуют отдельной проверки. Файл с настройками инструментов в `pyproject.toml` не выдаётся за устанавливаемый пакет. Ограничения и список зависимостей включены в README; служебные JSON анализа и подбора версий остаются в сервисе.

На первые два прохода модели выделены общие 15 секунд, на финальный — отдельные 15 секунд. При недоступном API или исчерпанной квоте сервис не имитирует попытки. Обычные правки и обновление страницы не открывают новые циклы; повторный анализ запускается отдельно. Для больших списков проблем форма показывает группы, полный список сохраняется в отчёте.

Python выбирается по метаданным и добровольно предоставленному снимку среды. Без них цель — явно отмеченные Python 3.11 / Linux x86_64. Lock описывает **новую совместимую среду**, а не восстановленную историческую среду автора. Статический анализ и успешный подбор пакетов не доказывают правильность вычислений.

## Развёртывание на Linux VM

Требуются Python 3.11+, Docker Engine с Linux-контейнерами, работающими лимитами cgroups и Docker Compose v2 или новее. Образы собираются на VM. Каноническая конфигурация — `deploy/production-compose.yaml`.

Внешний HTTPS-origin должен быть известен заранее. Для существующего HTTPS-прокси или туннеля:

```sh
python3 deploy/configure.py --origin https://public.example.org
docker compose --env-file .env -f deploy/production-compose.yaml --profile build build
docker compose --env-file .env -f deploy/production-compose.yaml up -d
```

Настройщик проверяет Docker, определяет GID сокета и создаёт корневой `.env` с правами `0600` и случайным внутренним токеном. Секреты не печатаются; существующий `.env` не перезаписывается. Не копируйте пример конфигурации вместо запуска настройщика. Для подготовки вне VM доступны `--skip-runtime-check --docker-gid GROUP_ID` и `--output PATH`.

Для DeepSeek перед запуском настройщика передайте `DEEPSEEK_API_KEY` через приватное окружение процесса; необязательный `DEEPSEEK_MODEL` по умолчанию — `deepseek-flash`. Ключ сохраняется только в приватном `.env` и передаётся контейнеру logic. Без ключа статический анализ и автоматический подбор версий продолжают работать. Не помещайте секреты в `VITE_*`, Git или аргументы команд.

### Собственный HTTPS-домен

Направьте DNS домена на VM и откройте входящие TCP-порты 80 и 443. Затем вместо настройки для внешнего прокси используйте:

```sh
python3 deploy/configure.py --origin https://public.example.org --domain public.example.org
docker compose --env-file .env -f deploy/production-compose.yaml --profile build build
docker compose --env-file .env -f deploy/production-compose.yaml --profile edge up -d
```

Профиль `edge` запускает Caddy с автоматическим HTTPS. Он выключен по умолчанию. Имя домена должно совпадать с origin; произвольный IP или временная ссылка туннеля для этого профиля не подходят.

### Проверка и обслуживание

```sh
docker compose --env-file .env -f deploy/production-compose.yaml config --quiet
docker compose --env-file .env -f deploy/production-compose.yaml ps
curl --fail http://127.0.0.1:8010/healthz
curl --fail http://127.0.0.1:8082/api/healthz
docker compose --env-file .env -f deploy/production-compose.yaml logs --tail 100 logic dispatcher web
```

Интерфейс с регистрацией и `/api` слушает `127.0.0.1:8082`; внутренний API — `127.0.0.1:8010`. Публичный прокси направляйте только на 8082. В режиме аккаунтов необходим HTTPS: cookies сессий защищены флагом Secure. Внутренний API не публикуйте в интернет.

SQLite и файлы задач находятся в volumes `nishtyak-logic_jobs` и `nishtyak-preview_preview`; сертификаты Caddy — в отдельных томах. Для резервной копии остановите пишущие контейнеры и сохраните оба тома и приватный `.env`. При обновлении сначала сохраните резервную копию, затем пересоберите образы и выполните `up -d`. `down` сохраняет данные; `down -v` удаляет тома.

Этот выпуск мигрирует прежние сроки хранения проектов в бессрочное хранение. Для отката на выпуск с TTL восстановите его резервную копию томов при остановленных процессах: старый код не должен открывать уже мигрированную базу.

При переходе со старых отдельных Compose сначала остановите старые logic/dispatcher/preview без удаления томов. Новый состав использует прежние имена томов и порты: одновременно запускать оба состава нельзя. Этот профиль рассчитан на одну VM и один экземпляр каждого процесса; горизонтальное масштабирование SQLite и диспетчера не предусмотрено.

## Компоненты и безопасность

- **Vue 3 / TypeScript / Pinia** — загрузка, прогресс, одна форма уточнений и скачивание.
- **`nishtyak_web` / FastAPI** — интерфейс, регистрация, Argon2id-пароли, серверные сессии, команды, приглашения и проверка прав на проекты.
- **`nishtyak_service` / FastAPI** — внутренний API, очередь в SQLite, состояния, ревизии решений, доказательный поиск пакетов, подбор версий и ограниченный цикл DeepSeek.
- **Dispatcher** — забирает задачи из очереди и создаёт отдельный контейнер анализатора через Docker socket. Сети и ключей модели у него нет.
- **`nishtyak_core`** — статический анализ через `ast`, `tomllib`, `packaging`, `stdlib-list`, разбор Conda через PyYAML, генерация файлов и ZIP.
- **Analyzer** — временный контейнер без сети, host mounts и секретов. Архив поступает через stdin, JSON-отчёт возвращается через stdout.

Основные процессы работают от UID 65532 с read-only filesystem, сброшенными capabilities, `no-new-privileges`, отдельным tmpfs и лимитами памяти, CPU и PID. Root используется только для начальной установки прав томов. Caddy дополнительно получает `NET_BIND_SERVICE` для портов 80/443.

Проверки ограничивают размер и состав ZIP, пути и выход за корень; найденные секреты исключаются из отправки модели и подготовки пакета. Модель имеет только инструменты чтения. Текст проекта и ответы инструментов считаются недоверенными: явные попытки подменить инструкции отфильтровываются, команды установки и ссылки из сгенерированного описания отклоняются. Фильтр дополняет строгую схему ответа и независимую проверку предложений, но не гарантирует обнаружение любой промпт-инъекции.

В серверном сценарии перед принятием пакета от модели, сохранением lock и выдачей готового ZIP выполняется запрос к OSV по именам и версиям PyPI-пакетов; исходники и секреты туда не передаются. Известные вредоносные релизы (`MAL-*`) блокируют выдачу, обычные известные уязвимости отмечаются в отчёте. Если проверка недоступна или неполна, выдача также блокируется. Ответы кэшируются в памяти до 10 минут. Отсутствие записи в базе не доказывает безопасность неизвестного пакета. Проверка не устанавливает пакеты; подбор через `uv` допускает wheel, исключает source builds и пользовательские hooks. Зависшие операции прерываются по таймаутам.

Просмотр готовых файлов читает именно собранный ZIP и проверяет его SHA и права участника. Большие тексты показываются частично; бинарные файлы и секреты не выдаются как текст. Markdown обрабатывается через `markdown-it` и DOMPurify, подсветка — через `highlight.js`. HTML из проекта и внешние изображения не загружаются.

Docker socket получает **только доверенный dispatcher**: доступ к нему позволяет управлять хостом. Изоляция анализатора не отменяет эту границу доверия. Для работы с недоверенными загрузками используйте выделенную VM и ограничивайте доступ к Docker, `.env` и резервным копиям.

Приглашение создаётся как одноразовая ссылка с ролью; ссылку передают самостоятельно. Почтовая доставка, подтверждение email и восстановление пароля не реализованы. Проекты, исходники и архивы хранятся до явного удаления; автоматического удаления по TTL нет. Квоты диска, лимиты запросов и таймауты операций сохраняются. Сроки сессий и одноразовых приглашений относятся к доступу, а не к хранению проекта.

## CLI

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[service,web]'
nishtyak analyze /path/to/project
nishtyak build /path/to/project --python 3.11 --lock \
  --target-platform linux-x86_64 --output /tmp/project.zip
```

CLI возвращает JSON. `--entry script.py`, `--module`, `--callable`, `--extra`, `--source-root` и `--package MODULE=REQUIREMENT` позволяют явно уточнить пакет. `--lock` требует целевого Python и платформу; без него формируется объяснимый черновик зависимостей. Dockerfile подготавливается автоматически для поддерживаемого профиля; `--no-docker` отключает его, а `--docker` явно запрашивает и проверяет возможность его создания. Для установки дополнительных возможностей Conda доступен extra `conda`.

```sh
nishtyak environment > /tmp/author-environment.json
nishtyak analyze /path/to/project --author-environment /tmp/author-environment.json
nishtyak conda /path/to/project
```

`environment` запускается самим автором в его окружении и читает метаданные установленного Python и дистрибутивов. JSON можно загрузить в сервис. Исходный Conda YAML сохраняется в ZIP и проверяется статически; подробная проверка доступна также командой `conda`. Сгенерированный корневой `environment.yml` использует проверенный pip-lock, но не фиксирует каналы и базовые пакеты Conda. Автоматическое разрешение и экспорт полного Conda-lock не реализованы. Генерируемый Dockerfile рассчитан на pip-зависимости, а исходный Dockerfile автора сохраняется отдельно вместе с проектом. Сборочные hooks `pyproject.toml`, образы и загруженный код сервис не выполняет.

## Разработка и поставка

В Git-репозитории доступны тесты. Требуются Python 3.11+ и Node.js 24. Установите `pip install -e '.[service,web,dev]'` и `npm ci`. В отдельных терминалах запустите процессы с одинаковым приватным `NISHTYAK_SERVICE_TOKEN` у обоих Python-процессов:

```sh
nishtyak-service dev --port 8010
nishtyak-web --port 8020
npm run dev
```

Откройте `http://127.0.0.1:5173`. Локальный режим использует одну рабочую область без регистрации. `dev` использует subprocess и подходит только для разработки; production использует Docker-анализатор.

```sh
pytest -q
ruff check src tests deploy/configure.py tools/build_release.py
ruff format --check src tests deploy/configure.py tools/build_release.py
npm test
npm run build
python3 tools/build_release.py --output ../nishtyak-final
```

Сборщик создаёт `nishtyak-0.3.0.tar.gz` и отдельный JSON-манифест с SHA256 архива и файлов. В поставку входят исходники, frontend assets, метаданные пакетов, README и production-конфигурация; Git, тесты, спецификации, дневники, `.env`, ключи и рабочие данные исключены. Сборка детерминирована для одинаковых исходников; базовые Docker-образы и доступность внешних индексов следует учитывать при обновлениях.
