# Статус разработки и дальнейшая работа

Ядро и самостоятельный сервис логики реализованы. Наш участок включает HTTP сервиса, постоянную очередь, хранение, ownership, TTL, анализ, планирование и экспорт. Второй разработчик делает пользовательский backend, аутентификацию пользователей и frontend. Цель — VM на Vast.ai; локально проходят 382 теста и Ruff. Сервис развернут на Linux VM: Docker isolation/cgroups/таймаут/cleanup, HTTP и восстановление очереди после рестарта проверены; результаты в examples/service-verification.json.

При чтении lock-файлов учитывать целевой Python/OS и происхождение. Точные версии не выводятся из AST; lock не объявляется проверенным без разрешенной среды или подтвержденного источника. Системные/CUDA требования не устанавливаются автоматически.

Локальная проверка E7 запускается пользователем явно на его машине или в его CI для разрешенного проекта. Сервер остается статическим анализатором загрузок. Импортированный отчет хранит происхождение: заявление автора или результат коллеги; ему не присваивается статус независимой проверки самого сервиса.

### Выпуски по результату

1. Рабочий пользовательский сценарий: корень проекта, декларации/extras, среда автора через HTTP, сохранение решений и интеграция frontend/backend. Готовность — два реальных проекта проходят весь путь до повторения коллегой.
2. Научный эксперимент: notebooks, полноценный манифест данных, несколько запусков, Conda и локальные отчеты проверки. Готовность — пакет содержит проверяемый сценарий и сравнимый ожидаемый результат.
3. Командный продукт: ревизии/diff/история, долгоживущие проекты, клиент/CI/уведомления, наблюдаемость и проверенное обновление. Готовность — повторная загрузка сохраняет работу, изменения объяснимы, восстановление проверено.

Для E8/E11 разделить долгоживущий проект, неизменяемую ревизию, короткую задачу обработки, решения, артефакт и отчет проверки. Текущий TTL одноразовой загрузки не подходит для истории проекта: сохранение требует явной политики хранения и квот. Логин и пользовательские сессии остаются у второго backend; наш сервис хранит проектные данные и проверяет доступ к ним. Новые сущности вводятся по мере реализации функций, с миграциями и обновлением OpenAPI.

### Первый инкремент: структура проекта

Сейчас ArchiveReader сохраняет обертку архива, а ManifestReader ищет requirements/pyproject только в корне. В `repo-main/main.py` импорт соседнего helper может стать unresolved. `src` layout работает при явно заданных source_roots, но подсказок корня нет.

Добавить явную модель структуры проекта: project root, source roots и рекомендуемые точки запуска. Автоматически выбирать только однозначную структуру, неоднозначную возвращать для уточнения. Сохранять оригинальные относительные пути и согласовывать чтение манифестов, imports и RunSpec. После изменения параметров анализа решения со старым analysis_id неприменимы.

### Второй инкремент: зависимость можно исправить

Сейчас excluded_modules относится к импортам и не удаляет явно объявленное требование из requirements. Optional dependencies в pyproject представлены предупреждением, выбрать группы через решения нельзя.

Дать декларациям стабильные ID и происхождение (файл/строка/группа), добавить явные действия сохранить/заменить/исключить и selected extras. Разделять факты исходного анализа и разрешенные пользователем вопросы, чтобы исправленный конфликт не удерживал план в draft. Ошибки решений должны содержать конкретный code и поле/ID декларации, без пользовательских секретов в сообщениях.

### Следующие прикладные шаги

Снимок среды уже поддержан библиотекой и CLI; HTTP и worker его пока не принимают. Довести этот поток до сервиса с отдельной валидацией и лимитом. Среда сервера не заменяет среду автора; импорт не доказывает успешный запуск проекта.

Сейчас POST plan не сохраняет отдельный документ решений. Сохранять решения с revision и отдавать их при повторном открытии; план остается производным от серверного отчета и решений. Обновление решений, удаление и TTL должны сохранять нынешние гарантии ownership и квот.

Каждая итерация завершается примерами входа/выхода, необходимыми регрессиями, экспортом актуального OpenAPI и проверкой на VM. Изменения схем private worker и сохраненных отчетов учитывают совместимость уже принятых задач. Новый функционал проходит через общие модели ядра; backend и frontend его не дублируют.

## Критерий защиты

Первый участник загружает собственный проект, объясняет отчет и уточняет зависимости. Второй получает ZIP и повторяет эксперимент по README в новой среде. Верификация установки, запуска и результата фиксируется отдельно. Для неопределенного случая инструмент показывает ограничение и следующий шаг.
