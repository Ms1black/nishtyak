# Статус разработки и дальнейшая работа

Ядро и самостоятельный сервис логики реализованы. Наш участок включает HTTP сервиса, постоянную очередь, хранение, ownership, TTL, анализ, планирование и экспорт. v0.2.0 принят на VM и проверен на двух публичных проектах: исходные результаты повторены в чистых venv и в контейнерах из экспортированных Dockerfile. v0.3.0 завершен: автоматический запуск, полный статический граф, stdlib выбранного Python, wheel-only lock через uv и инструментальный DeepSeek. Приемка: 665 тестов, VM isolation/HTTP, два подготовленных проекта в чистых venv, живой entrypoint/README и сохранение lock после рестарта; результаты — examples/resolution-verification.json.

Фронтенд из `web` объединен с `service-logic`. Добавлен браузерный шлюз к внутреннему сервису: загрузка, реальные статусы, безопасный предпросмотр, решения с ревизиями, автоматический запуск, переанализ, extras, граф, lock, AI с подтверждением и экспорт. Удалены проектные seed-моки, фиктивные планировщик и ZIP. Локальный режим не подменяет регистрацию: вход, команды, приглашения и проверку пользовательских сессий продолжает второй разработчик; для его backend предусмотрена доверенная proxy-граница. Проверки включают 16 HTTP-тестов шлюза и 6 тестов координации запросов фронта, production build и реальный браузерный путь `.py`/ZIP. Дальнейшая интеграция авторизации описана в API_CONTRACT.md.

Приемка веб-интерфейса на VM: `examples/web-verification.json`. Проверены реальная загрузка/предпросмотр/сохранение/экспорт/удаление, lock, Dockerfile, один живой AI-запрос с подтверждением и сохранность решения/lock/ZIP после рестарта шлюза. Установленные 61 Python-файл и 30 файлов статики совпали с проверенной сборкой.

Результаты приемки v0.2.0: `examples/workflow-verification.json`. Проверены HTTP, Docker isolation/cgroups/таймаут/cleanup, сохранение решений при перезапуске API и повторный анализ того же ZIP. Историческая проверка очереди сохранена в `examples/service-verification.json`.

При чтении lock-файлов учитывать целевой Python/OS и происхождение. Точные версии не выводятся из AST; lock не объявляется проверенным без разрешенной среды или подтвержденного источника. Системные/CUDA требования не устанавливаются автоматически.

Локальная проверка E7 запускается пользователем явно на его машине или в его CI для разрешенного проекта. Сервер остается статическим анализатором загрузок. Импортированный отчет хранит происхождение: заявление автора или результат коллеги; ему не присваивается статус независимой проверки самого сервиса.

### Выпуски по результату

1. Рабочий пользовательский сценарий: корень проекта, декларации/extras, среда автора через HTTP, сохранение решений и интеграция frontend/backend. Готовность — два реальных проекта проходят весь путь до повторения коллегой.
2. Научный эксперимент: notebooks, полноценный манифест данных, несколько запусков, Conda и локальные отчеты проверки. Готовность — пакет содержит проверяемый сценарий и сравнимый ожидаемый результат.
3. Командный продукт: ревизии/diff/история, долгоживущие проекты, клиент/CI/уведомления, наблюдаемость и проверенное обновление. Готовность — повторная загрузка сохраняет работу, изменения объяснимы, восстановление проверено.

Для E8/E11 разделить долгоживущий проект, неизменяемую ревизию, короткую задачу обработки, решения, артефакт и отчет проверки. Текущий TTL одноразовой загрузки не подходит для истории проекта: сохранение требует явной политики хранения и квот. Логин и пользовательские сессии остаются у второго backend; наш сервис хранит проектные данные и проверяет доступ к ним. Новые сущности вводятся по мере реализации функций, с миграциями и обновлением OpenAPI.

### Реализованный инкремент: автоматическая подготовка и разрешение версий

ТЗ требует статический разбор, зависимости либо объяснимый черновик, README, ZIP и предупреждения. Поле main и точная версия каждой библиотеки не обязательны. Зависимости анализируются для всего выбранного проекта до выбора запуска; неизвестные версии и данные оставляют предупреждения, а черновой экспорт доступен.

`LaunchDetector` использует отдельные AST-факты схемы 3, декларации project.scripts и граф. Один вычислительный experiment.py не требует main guard. Для пакета сохраняются относительные импорты через module launch, для src/callable создается helper. Автоматическая команда помечена inferred и не выдается за выбор автора; несколько равноправных вариантов остаются кандидатами в README. README содержит фактическое дерево файлов.

Локальный резолвер проходит полное имя и соблюдает порядок source roots: pkg.missing не превращается в найденный pkg или новый пакет PyPI. Различаются символ и подмодуль в from-import, поддержаны namespace-порции и условный каталог вложенного скрипта. Граф хранит источники/evidence и обходит циклы. Удаление локального провайдера проверяется при планировании. Статическая недостижимость не удаляет файлы и runtime-декларации.

Готовые компоненты: ast, tomllib, packaging, stdlib-list. pipreqs и pigar служат независимыми ориентирами; их host environment и PyPI latest не принимаются за среду автора. Для простого графа Grimp не подключен. find_spec/modulegraph loader для пользовательских исходников не применяется.

uv подключен как отдельный opt-in: эффективные named pip-требования + явные Python/OS → wheel-only разрешение прямых и транзитивных версий → requirements.lock.txt с SHA-256 и dependency-lock.json. Это новый согласованный набор, не доказательство исходной среды или успешного эксперимента. URL/path/editable, сборки sdist и Conda этим режимом не разрешаются. CLI build поддерживает --lock --target-platform; обычная упаковка не требует lock. Подробная логика и ограничения описаны в CORE_ARCHITECTURE.md.

DeepSeek получил ограниченные project_tree/read_source/analysis_facts/launch_candidates. Он видит очищенный ограниченный контекст, не выполняет код и не открывает произвольные пути. Ответы проверяются по схеме и evidence; предложения README/пакета/кандидата не меняют решения автоматически. Без ключа детерминированный сценарий работает. Живые entrypoint/readme проверены на VM; результат сохранен в examples/resolution-verification.json.

Регрессии проверяют одиночный .py без guard, локальные цепочки/циклы/namespace, отсутствующие подмодули, from-symbol, соседние helper, затенение корней, несколько запусков, библиотеку без запуска, неизвестные версии, отсутствие исполнения и офлайн-контракт AI. Собственные экспортированные примеры с прямым, module и src/callable запуском выполняются отдельно как доверенные fixtures. Приемка v0.3 проверила HTTP, изоляцию, restart, два подготовленных проекта с установкой lock в чистых venv и живой AI. Приемка двух публичных проектов v0.2 сохранена отдельным историческим отчетом; она не выдается за новый прогон.

### Реализовано в v0.2.0

`LayoutDetector` возвращает `ProjectLayout` с корнем, source roots и кандидатами. Обертка ZIP сохраняется в путях; манифесты и анализ используют выбранный корень. Неоднозначный проект требует выбора. `ProjectLauncher` формирует переносимый `run_project.py` для src layout и `module:attribute`; исходный проект на сервере не устанавливается и не запускается.

`DependencyDeclaration` хранит требование и происхождение со стабильным ID. Автор выбирает extras и действия keep/replace/exclude. Удаленная декларация не возвращается через автоматическое предположение о пакете; оставшийся импорт требует явного решения. Исходный отчет сохраняется, конфликты плана пересчитываются. Неверные решения возвращают код и поле.

Снимок среды, явно собранный на машине автора, принимается через HTTP и передается worker. Для metadata действует отдельный лимит 256 КиБ; Docker использует ограниченный поток stdin, а не переменные среды. Наблюдаемая версия дополняет требование без версии, исходное ограничение сохраняется. Сведения среды не доказывают успешный запуск.

Документ решений сохраняется отдельно от плана. Чтение возвращает analysis_id, revision и выборы автора; запись использует атомарный compare-and-swap. Повторный анализ сохраненного ZIP создает новый job ID, очищает решения с увеличением revision, сохраняет исходные TTL и резерв квоты. Активные задания и операции защищены от такой замены.

`LogicClient` покрывает загрузку, ожидание, повторный анализ, решения, план, ZIP и удаление. Контракт OpenAPI обновлен. В v0.2.0 отчеты использовали schema 2; текущий кодек читает schema 1/2 и новые отчеты schema 3, включая старые options без project_root. Миграция SQLite добавляет среду и решения с сохранением прежних проектов. Реальное подключение пользовательского интерфейса остается совместной приемкой со вторым разработчиком.

Каждая итерация завершается примерами входа/выхода, необходимыми регрессиями, экспортом актуального OpenAPI и проверкой на VM. Изменения схем private worker и сохраненных отчетов учитывают совместимость уже принятых задач. Новый функционал проходит через общие модели ядра; backend и frontend его не дублируют.

## Критерий защиты

Первый участник загружает собственный проект, объясняет отчет и уточняет зависимости. Второй получает ZIP и повторяет эксперимент по README в новой среде. Верификация установки, запуска и результата фиксируется отдельно. Для неопределенного случая инструмент показывает ограничение и следующий шаг.
