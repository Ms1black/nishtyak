# Статус разработки и дальнейшая работа

Ядро и первая итерация серверного обработчика реализованы. API остается за вторым разработчиком. Целевое развертывание — Linux VM на Vast.ai, 8 CPU и 120 GB RAM. Проверки: 231 тестов, Ruff lint/format, установка wheel в отдельный venv и повторение двух собственных примеров с результатом `mean=4.00`. Контейнер еще не собран и не проверен на Linux.

## Выполнено

| Этап | Результат |
| --- | --- |
| Контракт | Типизированные модели и версия публичного JSON, примеры для разработчика API |
| Анализ | Снимок файлов, AST, локальные/стандартные/внешние модули, неопределенности |
| Манифесты | requirements и стандартный pyproject с сохранением markers и ограничений |
| Планирование | Решения автора, запуск, версии, состав пакета, состояния готовности |
| Генерация | README, requirements, отчет и детерминированный ZIP |
| Инспекция | README/LICENSE, входные файлы, секреты, очистка сериализуемых данных |
| AI | Необязательный DeepSeek, очищенный контекст, проверка ответов, отказоустойчивость |
| Расширения | Dockerfile, отдельное чтение Conda, метаданные среды автора |
| Проверка | Два учебных проекта, новые venv, ожидаемый результат, wheel |
| Прием ZIP | Проверка путей, типов записей и размеров без распаковки на диск |
| Обработчик задач | Новый процесс, таймаут, лимиты и ограниченный типизированный JSON |
| Контейнерный профиль | Dockerfile, Compose и запуск одной задачи с очисткой |

Исправлены ошибки: исключение локального модуля теперь блокирует сломанный пакет; обычная папка `env/venv` не теряется как виртуальное окружение; поиск секретов не повторяет линейный подсчет строк для каждого совпадения; снимок отклоняет конфликт файла и каталога.

Спецификации доступны в [архитектуре](CORE_ARCHITECTURE.md), [контракте API](API_CONTRACT.md), [OpenAPI](openapi.yaml) и [серверном профиле](SERVER_RUNTIME.md). Машинные примеры находятся в `examples/contracts/`. Полный локальный журнал исследований и промежуточных запусков хранится отдельно от исходного кода.

## Очередность инкрементов

| Приоритет | Работа | Ответственный | Готово, когда |
| --- | --- | --- | --- |
| P0.1 | Собрать и проверить worker на VM: UID, сеть, mounts, CPU/RAM/PID, timeout и уборка | Ядро / развертывание | Реальный отчет получен; ограниченные задачи завершаются и не оставляют контейнеров |
| P0.2 | API загрузки и задач, строгие DTO, серверное хранение, ограниченная очередь | Второй разработчик | Upload дает 202; после опроса доступен отчет, перегрузка обрабатывается явно |
| P0.3 | Владение задачей, plan/bundle, срок хранения и удаление | Второй разработчик | Чужой проект недоступен; старые решения отклоняются; ZIP скачивается; TTL удаляет данные |
| P0.4 | Фронтенд полного пути и публикация через HTTPS | Второй разработчик + совместная приемка | Пользователь проходит загрузку, уточнения и экспорт без CLI |
| P0.5 | Собственный проект команды и сценарии отказа на VM | Оба | Проект повторяется в новой среде; поврежденный ZIP, timeout и рестарт дают понятные статусы |
| P1.1 | Разрешение конфликтов отдельных деклараций, выбор extras, типизированные ошибки | Ядро | Решение автора отражается в плане без потери исходных evidence |
| P1.2 | Реальный DeepSeek: объяснение отчета, README, гипотезы пакетов | Ядро + второй разработчик | Проверен живой запрос, лимит расходов, таймаут и работа без AI |
| P2 | Conda-экспорт, профили других Python, дополнительные форматы | Ядро | Каждый профиль проверен отдельным примером; ограничения видны в UI |

P0.1 и P0.2 выполняются параллельно. До проверки контейнера API можно подключать к локальному AnalysisJobRunner на собственных тестовых проектах. Открывать прием публичных загрузок следует после P0.1–P0.5. Асинхронный контракт 202/job status согласован в OpenAPI; его реализацию нужно подключить вместе с API и фронтендом.

Для первого запуска достаточно одного диспетчера с двумя одновременно работающими контейнерами. Каждая задача получает 1 CPU и 512 MiB независимо от общего объема RAM. Начальные предложения по очереди и хранению приведены в SERVER_RUNTIME.md; масштабирование выполняется после измерения реальных проектов.

## Следующие улучшения ядра

| Задача | Причина | Проверка готовности |
| --- | --- | --- |
| Типизированные исключения | Точное отображение ошибок на HTTP-коды | Адаптер не разбирает текст ValueError |
| Явное разрешение отдельных деклараций | Можно исправить конфликт или убрать устаревшее требование | Сохраняются исходные evidence и решение автора |
| Выбор extras | Поддержка дополнительных групп pyproject | Выбранные группы входят в план, остальные сохраняются отдельно |
| Conda-план и генератор | Полный отдельный профиль среды | Conda и pip не смешиваются; инструкция соответствует профилю |
| Другие профили stdlib | Анализ целевого Python, отличающегося от хоста | Проверенный каталог с версией и тестами |
| Проверка Docker | Подтвердить работоспособность конкретного шаблона | Сборка и запуск собственного примера с зафиксированным результатом |

Новая функция добавляет читатель, правило или генератор и проходит через общий PackagePlan. Не следует дублировать определение зависимостей в API или фронтенде.

## Критерий защиты

Первый участник загружает собственный проект, объясняет отчет и уточняет зависимости. Второй получает ZIP и повторяет эксперимент по README в новой среде. Верификация установки, запуска и результата фиксируется отдельно. Для неопределенного случая инструмент показывает ограничение и следующий шаг.
